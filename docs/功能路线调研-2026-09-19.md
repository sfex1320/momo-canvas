# MOMO 智能画布功能路线调研

调研日期：2026-09-19。范围：Windows 桌面端、电商长图、图像生成与编辑、资产、ComfyUI 同步、导演台。本文只提供路线建议，不表示功能已经实现。依据是当前代码、近期维护记录与官方资料；优先级是产品判断，未经过用户规模统计或可用性实验。

## 判断

MOMO 已有较完整的创作链路。下一阶段最有价值的是让已经生成的内容能够找回、撤回、迁移、复用，并让用户在运行前知道工作流是否真正可用。建议先做下面的前两项，再完善模板管理和可验证交付；暂不增加新的独立工作台。

| 顺序 | 建议 | 级别 | 最直接的用户价值 | 首期规模 |
|---|---|---|---|---|
| 1 | 跨重启接回已提交任务 | P0 | 避免关软件后丢结果、误点重试重复生成 | 大，可先只覆盖 ComfyUI |
| 2 | 长图切片版本与采用机制 | P0 | 重生成不丢旧稿，选错可以恢复 | 中 |
| 3 | 模板归档、引用保护与恢复 | P1 | 日常精简工作流无需维护脚本，旧项目仍可打开 | 中 |
| 4 | 可运行性检查与实测记录 | P1 | 区分“已同步”“依赖齐全”“确实跑通” | 中 |
| 5 | 项目包完整性报告与安全导出 | P1 | 搬机器、备份交付时知道哪些内容真的带走了 | 中到大 |
| 6 | 电商锁定文案与交付检查 | P2；若电商为主可升 P1 | 防止型号、价格、规格、品牌字样在出图时漂移 | 中，批量 SKU 后置 |

规模是相对工程量，包含数据迁移、界面与验收，不是排期承诺。

## 1. 跨重启接回已提交任务

**已有基础。** `src/core/studio/jobCenter.ts` 有统一状态、取消与重试入口；`directorQueue.ts` 会标记中断的 Take；Comfy 服务已用 `prompt_id` 查询历史；通用协议执行器能够取得远程 `taskId`。助手失败后清理确认、不自动重试的现有行为必须保留。

**真实缺口。** 任务中心明确是会话状态，不落盘，`retryRun` 是内存函数。`recoverInterruptedTasks` 把运行中的 Take 标成错误，不能据服务端任务 ID 接回结果。`services/comfy.ts` 的 `promptId`、`services/customProto.ts` 的任务 ID 留在当前执行流程中。这与“完成了中断提示”不同，还没有完成“已提交任务恢复”。

**首期做法。** 持久化一个不含密钥的执行账本：所属画布/项目、请求输入快照、服务端任务 ID、服务连接引用、阶段和产物索引。重启先查询原任务，已完成则下载入库，仍运行则继续观察；下载失败只重试下载。明确分开“检查原任务”和“重新提交”。先接 ComfyUI，再为提供查询接口的远程适配器接入；没有任务查询能力时显示“状态未知，需要核对”，不能宣称可恢复或自动重发。ComfyUI 服务本身重启且历史丢失时也走未知分支。

**验收。** 分别在提交后、推理中、结果下载中关闭 MOMO；重开后已存在的服务端任务不重复 POST，成功产物只入库一次且写回原项目。另测任务历史过期、服务离线和已取消任务。同步返回图片且没有任务 ID 的协议明确不在第一期恢复保证内。

**官方依据。** ComfyUI 提供 `/queue`、`/history/{prompt_id}` 等状态接口，说明已有接回查询的技术基础；Krea 也把任务生命周期与按 ID 查询单列为公共 API 能力。这里只借鉴恢复模型，不要求接入 Krea 服务。[ComfyUI Server Routes](https://docs.comfy.org/development/comfyui-server/comms_routes)；[Krea Job Lifecycle](https://www.krea.ai/docs/developers/job-lifecycle)。

## 2. 长图切片版本与采用机制

**已有基础。** 普通生成节点已有 `GenHistoryEntry`、并排挑图和多模型对比；导演台有 Take、采用版本及派生修订；电商长图有分片重生、前后接缝参考、同组资产管理。不要再另做一套普通图片对比入口。

**真实缺口。** `src/core/stores/assetStore.ts` 的电商同组同槽收录会替换旧条目，并调用 `deleteAssetFile` 删除旧文件；`EcomSlide` 主要存一个 `img`，`EcomImageData` 主要存当前 `result`。因此需要保护的是电商重生成链路的历史稿，而不是增加“历史”按钮本身。

**首期做法。** 为每个切片保留候选版本和当前采用版本；生成新候选后先对比再采用。整张长图记录一份“各切片采用哪个版本”的合成快照；回退切片时标记整图需要重拼。旧版本按显式保留策略清理，清理前检查它是否仍被画布、项目包或采用快照引用。记录原输入、提示词、模型和实际参数，复用现有对比组件。

**验收。** 第三片连续重生三次后，可以恢复第一次，重启仍有效；重拼能追溯每一片的来源。一次重生失败不改变采用版本。清理未采用候选不破坏已采用整图，也不删除其他地方引用的文件。

**官方依据。** Invoke 的工作流结果先进入暂存区，由用户选择接受某一项再提交到画布；其参数召回还覆盖提示词、种子、模型与参考输入。这两个机制分别支持“先选择再采用”和“结果可复用”，不意味着 MOMO 要复制其整套界面。[Invoke Run Workflow on Canvas](https://invoke.ai/features/canvas/run-workflow/)；[Invoke Recall Parameters API](https://invoke.ai/development/guides/recall-api/)。

## 3. 模板归档、引用保护与恢复

**已有基础。** Comfy 同步已经有版本、差异、冲突处理、忽略规则、失联源文件保留和重新关联；模板管理已有删除和二次确认。近期 `docs/工作流盘点-2026-09-19.md`、`docs/助手连续创作与工作流整理-2026-09-19.md` 记录了精简 H3 和恢复放大模板的专用维护过程。

**真实缺口。** 当前 `comfyStore.remove` 是从列表过滤对象；模板管理删除入口没有同等的全局引用预演和软件内归档恢复流程。近期维护需要核对画布、项目配方、旧 ID、同步认领策略，再通过专用脚本实现，可作为真实痛点证据。

**首期做法。** 增加“归档”状态和归档页，保留 ID、模板正文及与 workflowId 的关联；新建节点默认只选活动模板，已有节点仍能使用或查看旧模板。删除前列出活动/归档画布、项目配方及历史快照引用；批量精简先预演“保留、归档、受引用保护”。恢复时保留旧 ID。归档语义要进入同步引擎，避免下次扫描又把归档模板加回活动列表，不能仅靠隐藏 UI。

**验收。** 被旧画布引用的模板归档后，原节点仍能解析；恢复不会产生重复 ID。来源重扫和应用重启都不让归档模板复活；同名但不同工作流不自动合并。删除带引用的模板必须先展示影响并提供归档替代路径。

**依据边界。** 此项主要来自 MOMO 自己的维护事实，不以竞品功能清单作为必要性证明。它应建立在现有同步和版本体系上。

## 4. 可运行性检查与实测记录

**已有基础。** `comfySync/classify.ts` 已区分前端备注与后端节点、递归检查已使用子图、提示疑似缺模型；`engine.ts` 在源文件未变时也会刷新依赖。导演台已有参考槽与视频规格预检。不能将“增加缺插件检测”列为新功能。

**真实缺口。** 现有同步健康点聚合同步状态，依赖告警主要解决类名及模型引用问题；这不足以说明某一模板的当前输入、参数类型、输出端、运行环境组合确实可执行。近期恢复记录中的参数类型修复，以及“静态校验不等于 GPU 实跑”，说明需要更清楚的证据层级。

**首期做法。** 同一张卡展示四层结果：源与服务连接、节点/模型依赖、当前请求输入校验、最近实测。静态检查补必填字段、枚举/布尔类型、有效输出与配方入口映射，离线时标未知；实测记录绑定工作流哈希和必要环境标识，显示时间、输入规格、耗时、结果，而非永久绿色“健康”。模板或环境变化使实测证据过期。给出定位到具体节点/字段的修复路径，不自动装包或更新环境。

**验收。** 备注节点零误报；缺模型、错误布尔值、输出口消失分别能定位；服务离线不显示已通过。旧模板跑成功后改一个关键节点，必须提示需要重新验证。静态检查不会意外提交生成任务。

**官方依据。** ComfyUI 官方把缺节点、缺模型、环境差异列为不同的工作流加载问题；其接口还提供节点定义与系统状态。MOMO 可以据此区分不同证据，但显存和速度仍需真实运行数据。[ComfyUI Missing Nodes / Workflow Won’t Load](https://support.comfy.org/articles/1536450065-missing-nodes-workflow-won-t-load)；[ComfyUI Server Routes](https://docs.comfy.org/development/comfyui-server/comms_routes)。

## 5. 项目包完整性报告与安全导出

**已有基础。** `directorProjectIO.ts` 已有 `.momoproject`：项目、素材、模板快照、导入重链接和内容指纹复用；`momoflow.ts` 已支持含素材的画布分享；绑定项目目录与 Take 镜像也已存在。这一项是强化现有迁移能力。

**真实缺口。** `exportProjectPackage` 收集资产时会跳过找不到有效路径的条目，但 `PackReport` 没有完整的缺失资产报告。`src-tauri/src/project_pack.rs` 对合法同名旧包先清理再复制，途中复制失败可能让原先完整的包消失。包清单虽有 hash 字段，目前读包与复制流程没有逐项计算并验证字节哈希的完整闭环。`.momoflow` 的外部依赖声明也不能替代实际运行环境核验。

**首期做法。** 导出前列清单：已收齐、缺失、离线、无法携带、外部模型/配方依赖；允许用户明确选择“完整备份”或“带缺失报告的部分包”。新包写到临时目录，逐项校验完成才提交，不提前删除上一次成功包。导入先检查媒体、指纹、模板和模型映射，再创建新项目，提供缺素材的批量重链接。包内保留媒体和流程引用，排除密钥、本机账号及不必要的绝对路径。

**验收。** 新电脑或空测试数据目录导入后，全部参考槽和采用 Take 能打开；篡改一个媒体文件能定位到具体条目。模拟磁盘空间不足或中途取消，上一次完整包仍可读。重导同包不重复复制已存在素材；缺模型时明确提示，不假称完全可复现。

**官方依据。** Invoke 的项目包明确保存图层、蒙版、参考图和参数，并明确模型本体不在包内；这提供了“可携带内容”和“外部依赖”分开声明的可用参考。MOMO 已有对应基础，应把完整性和恢复测试补齐。[Invoke Canvas Projects](https://invoke.ai/features/canvas/canvas-projects/)。

## 6. 电商锁定文案与交付检查

**已有基础。** `ecomPresets.ts` 已提取商品属性、卖点、配套文案和风格；长图支持先审提示词再出图，`ecomContinuity.ts` 统一接缝规则。放大和视频也已有各自质量检查。推荐的增量是面向商品交付的事实核对，不是再做泛化“AI 评分”。

**真实缺口。** 当前长图结构主要存描述文本、分析与切片结果，未见用户确认的“必须逐字一致字段”及成图与这些字段的核对记录。仅在提示词里重复品牌和规格，不能保证最终图片中的文字准确。

**首期做法。** 在长图现有流程加一张可复用商品卡，用户确认品牌、型号、规格、价格和必须原样呈现的文字；确认值在提示词优化时锁定。生成后检查缺片、尺寸、接缝，并用 OCR 或视觉识别把成图文字与确认值逐项对照，低置信度标为待人工核对。问题定位到切片和位置，允许只修这一片；检查不自动消耗生成额度。随后再考虑表格导入多个 SKU、套用同一模板、按 SKU 导出和失败项重跑，避免第一期把产品卡扩大成商品管理系统。

**验收。** 准备包含相近型号、数字、单位、价格、小字体和弯曲文字的样本集；逐条统计识别成功、漏检、误报，不能只看模型自评分。已知错字样本在人工确认前不能显示“已通过”。导出能说明每个切片对应哪份已确认文案及哪个采用版本。

**官方参考与推断。** Krea 的节点文档包含可确定设置字体、位置等的文字叠加工具，也将输入/输出暴露为可复用工作流表单。可借鉴的是把固定商业信息与可变视觉输入拆开；“商品字段锁定 + OCR 核对”是本项目建议，并非该官方文档已经证明的竞品能力。[Krea Nodes Workflows](https://www.krea.ai/docs/user-guide/features/nodes)。MOMO 当前风格文字是位图，不能因此承诺原生字体编辑。

## 推进顺序与排除项

先把第 1、2 项做成可验收的小闭环；第 3、4 项共用模板引用索引与运行证据，第 5 项复用这些依赖清单；第 6 项接第 2 项版本和采用机制。每一期只看几个结果：中断后找回率、重复提交次数、误删可恢复率、重新打开旧项目的成功率、一次交付前人工返工次数。

本轮不建议增加新的独立平面工作台、再造已有资产库/回收站/对比视图/语音入口、不以接入更多模型作为主目标，不推荐已被用户排除的分层模型路线。大型云协作、模板市场和全自动发布需要真实需求后再排。现有价格估算、并发限流、Comfy 同步、七工位和导演台导出能力优先继续复用。

本文进行了代码和资料核对，没有执行 GPU 生成、崩溃恢复或跨机器导入测试；以上验收标准是下一阶段实现时应完成的验证，不能读作当前软件已通过。
